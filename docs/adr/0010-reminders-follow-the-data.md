# ADR 0010: お知らせは「データに合わせる」方式で予約・取り消しする

- 状態：採用
- 日付：2026-10-25

## 状況

段階 C で、次の健診の前日の夜に届くお知らせ（ローカル通知）を作ります。要件定義 v0.4 では、次のことを求めています。

- データを先に保存し、成功してからお知らせを予約・取り消しする。保存に失敗したら、お知らせは変えない（S-05、R-45）。
- お知らせの予約や取り消しに失敗しても、アプリを開いたとき・前面に戻ったときに直す（S-06）。iPhone の取り消しの仕組み（`removePendingNotificationRequests`）は失敗を返さないので、取り消せたかは一覧を取り直して確かめる。
- 予定の変更と削除を続けて行っても、古い予約が遅れて終わって戻らないよう、処理は 1 つずつ行う（S-09）。
- 日付を変えた・消した・その日の健診後メモを保存した・元に戻した、のどれでもお知らせを正しくする（R-45）。

操作ごとに「予約する」「取り消す」を書き分けると、操作が増えるたびに漏れが出やすく、失敗したときに直す道もありません。

## 決定

- 操作ごとにお知らせを書き分けず、「次の健診」から“あるべきお知らせ”を決め、予約中のお知らせと突き合わせて、足りなければ予約し、余分なら取り消す（`ReminderPlan.actions`）。
- 突き合わせは、保存の窓口を通した操作のあと（`NoteStore.perform`）、アプリを開いたとき、前面に戻ったときに行う（`ReminderSync.requestSync`）。
- お知らせの名前に届く日時を入れる（例：`next-checkup-reminder-202611072100`）。日時が変われば名前も変わるので、名前を比べるだけで古いお知らせを見分けられる。このアプリのお知らせは名前の頭で見分け、ほかには触れない。
- 処理は 1 つずつ順に行う。処理中にまた頼まれたら、終わってから最新のデータでもう一度合わせる。
- お知らせがオフ・通知の許可がない・届く時刻がもう過ぎた（遅れて届かせない、R-41）ときは、“あるべきお知らせ”はない。
- iPhone の通知の仕組みは `ReminderCenter` で包み、テストでは偽物に差し替える。開発用ビルドでは、予約を失敗させる切り替えを設定の「開発用」に置く（S-08）。

## 理由

- どの操作のあとでも同じ「合わせる」を呼ぶだけなので、新しい操作を足しても書き漏れが起きない。元に戻すで予定が戻ったときも、そのまま正しくなる。
- 失敗しても、次に合わせるときに直る（S-06）。取り消しの成否も、一覧を取り直すことで確かめられる。
- 決まり（`ReminderPlan`）は値だけで計算できるので、通知の仕組みなしでテストできる。

## 影響

- 操作のたびに一覧の取り直しが走るが、予約中のお知らせは多くても 1 件なので、負担は小さい。
- 予約に失敗したときは、`ReminderSync.lastScheduleFailed` を見て、画面のカードに「お知らせを予約できませんでした」と出す（段階 C の画面、C2）。
- 通知の許可を聞くのは、初めてお知らせをオンにしたとき（R-44、C2）。
