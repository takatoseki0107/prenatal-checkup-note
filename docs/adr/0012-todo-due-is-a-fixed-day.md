# ADR 0012: やることの期限は選んだ日付で持ち、完了は 2 段階にする

- 状態：採用
- 日付：2026-10-27

## 状況

妻の意見から「やること」を足します（要件定義 v0.4 の 5.10、R-100〜R-110）。先生に「この日までにやっておいて」と言われる申請や、産院への連絡などを書いておく機能です。触れる見本（`Todo.dc.html`、`TodoLink.dc.html`）で、開発者と形を決めました。

保存の形を決める前に、次の 2 つを決める必要がありました。

- 期限の「次の健診まで」。次の健診の日付とつないでおけば、予定を変えたときに期限も一緒に動く。ただ、次の健診は健診後メモを保存すると空になり、新しい予定を入れ直すので、つなぐ相手が消えたり変わったりする。
- 完了。丸を押した瞬間に完了にして一覧から消すと、押し間違えたときに何が起きたかわかりにくい（見本で開発者が指摘した）。

## 決定

- やることのモデル `TodoItem` を足す。ほかのモデルと同じく、作ったときから変わらない ID（UUID）を持つ。
- 期限は、選んだときの日付を `CalendarDay.number`（例：20261109）でそのまま持つ（`dueDayNumber`）。「次の健診まで」も、押したときの次の健診の日付を入れるだけで、次の健診とはつながない。あとで次の健診の日付を変えても、期限は動かさない。
- 完了は 2 段階にする。丸を押すと `isChecked`（緑のチェック）が付き、一覧のその場に残る。「チェックした n 件を完了にする」で `completedAt` に日時を入れ、「完了したこと」に移す。聞きたいことの「丸を付ける → 健診後メモを保存すると移る」と同じ考え方。
- 並べ方・数え方（見出し、次の健診の線、タブの数、健診予定のカードの数）と期限のボタンは、画面から切り離した `TodoList` と `TodoDueChoice` で決め、単体テストで確かめる。
- 健診後メモから足したやることは、そのメモの受診日を `originVisitDayNumber` に持ち、「◯月◯日の健診で」と出す。メモとは関係（`@Relationship`）でつながない。

## 理由

- 期限が勝手に動かないので、「次の健診の日を直したら、やることの期限まで変わった」が起きない。期限を変えたいときは、やることの「直す」で変えればよい。
- 次の健診とつながないので、健診後メモを保存して次の健診が空になっても、やることには何も起きない。決まりが増えず、テストもしやすい。
- 完了を 2 段階にすると、押し間違えてもその場で外せる。完了にしたあとも「元に戻す」で、チェックが付いた状態に戻せる（R-104、R-60）。
- 関係を使わず、モデルを足すだけなので、いまのデータはそのまま開ける（自動の移行。ADR 0011 と同じ）。

## 影響

- 次の健診の日付を変えたとき、「次の健診まで」で入れた期限は古い日付のまま残る。見本で開発者と確かめたうえでの決定（要件定義書 R-102）。困る声があれば、F4 の妻の確認のあとで考え直す。
- 期限の日のお知らせは、最初の版には入れない（要件定義書 5.10）。

## 追記（2026-10-28、健診後メモから足す）

健診後メモの画面から、やることを足せるようにした（R-107）。

- やることに `originMemoID`（足したメモ、または書きかけの ID）を足した。メモとは関係でつながず、ID で指す（ADR 0011 の写真と同じ考え方）。書きかけの ID は保存したメモの ID と同じなので、書いている途中に足したやることも、保存したメモの画面から見える。メモを削除しても、やることは残る。
- 健診後メモから足すときは、期限を最初「期限なし」にする。メモを書いている時点の「次の健診」は、たいてい書いている日の健診（保存すると空になる）なので、その日がメモの受診日と同じなら「次の健診まで」のボタンを出さない（`TodoDueChoice.offeredNextCheckupDay`）。次の健診の日付を入れ直したあと、やることの「直す」で期限を変えられる。
- モデルに省略できる値を足すだけなので、いまのデータはそのまま開ける。
